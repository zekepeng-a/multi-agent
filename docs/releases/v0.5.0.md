# V0.5.0 — Architecture Frozen

Released: 2026-09-27 · Commit: see tag `v0.5.0` · Runtime: `node >= 24` (verified on v24.19.0)

## 1. Release status

**V0.5.0 is released as a frozen architecture.** The V0.5 line closed with **zero known blockers**, a **142/142 green test suite**, and mechanically verifiable artifact identity across the Planner pipeline.

> **V0.5 is frozen. Remaining items are technical debt / observations and are intentionally deferred to V0.6.**

Scope of this release (all already implemented and verified, nothing forward-looking):

| Area | Status |
|---|---|
| Core orchestration (Planner → DAG → Executor → Validation → Review → Evaluator → Replan → Memory) | stable |
| Planner artifact lifecycle (R1) | consolidated, single owner |
| Artifact / run identity (R3) | implemented, mechanically checkable |
| Memory (derived layer) + Retriever + Context + State Summary | stable |
| Review safety semantics (no valid verdict ⇒ no PASS) | preserved |
| Memory use attribution (auditable self-attribution) | implemented |

## 2. Core capabilities

- Two-phase Planner (expert judgment → real expert consultation → consolidated plan + task DAG)
- Plan Precheck (7 checks) before execution
- Task DAG with dependency resolution, **bounded parallel batches**, and **file-conflict protection**
- Unified Executor: `claude-code` / `dsh-headless` / `codex`, one shared Result/Error contract
- Validation via executable acceptance criteria (`run:` / `file:`), with command normalization
- Review Gate with an independent Reviewer, conservative FAIL fallback and infrastructure-failure classification
- Evaluator (transient failure vs plan problem) → **local Replanning** with a bounded retry/replan budget
- Agent communication (Manager-mediated file message channel) and run observability (`.ai/runs/*.json` + JSONL)
- **Project Memory** as a derived layer: Distiller → `memory/{decisions,knowledge,lessons,agents}` → Retriever → Context Assembly (token budget) → State Summary → Planner
- Lifecycle auto-refresh of Memory and State Summary after every batch
- **Memory use attribution**: the Planner declares `plan.memory_refs`; the runtime validates each reference against the memories that actually entered the current planner context

## 3. R1 — Planner Lifecycle Refactor

Before R1, the "is the Planner done?" decision was spread across a generic file-wait helper and a stack of ad-hoc predicates (size stability, semantic non-emptiness, staleness window, shape check) — four separate fixes for four separate symptoms.

R1 consolidated this into one explicit lifecycle owned by a single module:

```
DRAFT(.tmp — the LLM may write nothing else)
  → VALIDATED(validatePlannerArtifact(kind = stage1 | stage2 | replan))
  → FINALIZED(.done marker, or degraded stability_fallback)
  → PUBLISHED(publishPlannerArtifact: identity injected, final written)
  → ACCEPTED(consumed as the same artifact)
```

- **Single owner**: `planner-lifecycle.mjs` holds all planner domain validation, finalization, publishing and identity logic.
- **Generic tool restored**: `file-wait.mjs` only answers "does the file exist / is its size stable / does it parse as JSON". The orchestrator no longer performs planner lifecycle decisions itself.
- **One entry point**: stage 1, stage 2 and replan all run through the same `runPlannerStage` → `finalizePlannerOutput` path.
- **Stage shape is explicit**: the artifact kind (`stage1` / `stage2` / `replan`) is passed in, never inferred by shape guessing.
- **Finalization mode is recorded on the artifact** (`plan.finalizationMode`): `marker` is the normal path, `stability_fallback` is a degraded path — they are never conflated.

## 4. R3 — Artifact Identity

Every planner artifact now carries:

| Field | Meaning |
|---|---|
| `planId` | identity of one planner artifact (`plan-<kind>-<seq>-<nonce>`; not derived from task id or wall clock) |
| `parentPlanId` | the previous plan in a replan chain (`null` for the initial plan) |
| `rootPlanId` | the root of the replan chain |
| `planDigest` | content fingerprint: `sha256` over the canonicalized plan + tasks, with identity fields excluded |
| `finalizationMode` | `marker` or `stability_fallback` |

The same identity is written to the plan artifact, `tasks.json` (`plan.*`), `_memory-attribution.json` and `runs/*.json`, making `Plan → Task → Run` traceable.

`verifyArtifactIdentity()` mechanically checks the chain — accepted vs published, tasks vs accepted, attribution vs accepted, and each run against its owning plan — and reports `identity_mismatch` instead of silently accepting a mismatched artifact.

## 6. Known technical debt

Recorded, deliberately **not** fixed in V0.5.0:

1. **Fallback DAG bypasses the planner lifecycle.** When planning fails, the Manager synthesizes a template plan that carries no `planId`/`planDigest` and no `plan_source` marker, and its acceptance criteria are hardcoded (`file: server.js`, `run: node test.js`), which does not match arbitrary project types.
2. **Precheck has no recovery contract.** Precheck failure exits the run; the commented-out intent to feed `precheck.json` back into replanning was never implemented, and `precheck.json` currently has no consumer.
3. **Replan does not pass through Precheck** (asymmetric with the initial plan).
4. **No automated real-E2E layer.** End-to-end runs against a live worker CLI are performed manually; the suite covers unit / integration / controlled-time levels only.
5. **`stability_fallback` has become a common finalization path** (observed on stage 2 in real runs) because the explicit `.done` marker is not always written by the model. It still produces a valid, complete, identified artifact.
6. **`blocked` tasks have no owner** — a task blocked by a failed dependency is never retried, replanned or surfaced.
7. **`evaluateFailure` classifies failures by string matching** on the failure history, so new failure kinds can silently fall through.
8. **`tasks.json` mixes two lifecycles** (plan artifact and per-task state), and `.ai/results/` holds several kinds of artifacts in one directory.

## 7. V0.6 boundary

- V0.5.0 contains **no** V0.6 functionality, no new agents/models, no model routing, no vector database or embedding retrieval, and no hooks framework.
- The items in §6 are the V0.6 backlog candidates; none of them block the V0.5 freeze, and none of them are silently patched in this release.
- V0.6 work must preserve the V0.5 invariants: only finalized artifacts are accepted; accepted = published = attribution = tasks = run identity; replan gets a new `planId` with `parentPlanId`; canonical digests are stable; no valid reviewer verdict means no PASS; validation evidence reaches the review; memory use stays auditable.
- The planner lifecycle module must remain the only owner of planner domain logic, and the generic file-wait helper must not regain planner semantics.
